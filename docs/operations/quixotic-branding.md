# Quixotic 品牌独立与验收计划

目标是让用户从安装、启动、配对、远控到升级，都能确认自己运行的是 Quixotic，并知道软件将连接哪台机器、从哪里取得更新。已有 Linux 数据和已配对设备需要继续工作。

| 使用场景 | 实施范围 | 验收方法 |
| --- | --- | --- |
| Windows、Linux 桌面及 Web | 安装器、图标、托盘、启动页、设置、升级弹窗、错误提示和翻译 | 检查构建产物及界面，打开“共享和访问”，确认两个配对入口和更新来源 |
| Android 和 iOS | 应用名、包标识、图标、系统权限文案、深链、组件与更新配置 | 展开生产 Expo 配置，检查应用归属、已声明的域名、签名关联和 OTA 项目，再测扫码解析 |
| 设备互联 | EasyTier 电脑直连、手机公网 HTTPS、已有授权和会话链接 | 在隔离环境分别生成两类链接，核对目标主机与端口，验证当前客户端和既有链接格式 |
| 命令行和更新 | 桌面可执行文件、CLI、安装脚本、SSH 引导、升级源 | 在临时目录测试帮助、版本和安装。检查缺少自有发行物时的行为，以及旧命令的兼容路径 |
| 对外分发 | 项目主页、下载入口、用户文档、构建和发布流程 | 从用户指引追踪到自有仓库或本机产物，核对不会把用户导向上游商店、软件包或更新服务 |
| 升级与数据 | 环境身份、数据库、凭据、配对记录、托盘后台运行 | 使用临时目录和测试数据验证路径优先级、授权与启动，保留当前运行环境供用户继续使用 |

### 配置边界

- 私有部署使用设备上保存的 EasyTier 地址和公网 HTTPS 地址。默认构建不假定项目有公共中继、登录服务、应用商店条目或 Expo 更新项目。
- Linux 已有 `/usr/bin/quixotic` 桌面入口。命令行使用独立的 `quixotic-cli` 名称，并核对既有 `t3` 调用的行为。
- 上游 MIT 版权声明、第三方许可、来源与商标说明应如实保留。旧数据目录、已存储键、旧客户端使用的协议与已发布链接按兼容性验证。
- 验收记录要区分源码与配置检查、实际生成的产物、自动化测试、真机验证。发布、替换正在运行的服务器和分发签名各有独立步骤。
